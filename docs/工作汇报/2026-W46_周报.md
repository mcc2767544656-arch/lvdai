## 二、工作背景

上一周已完成 Orange Pi 5 Pro 的 40Pin PWM 引出、UM982 双天线接入、CORS 账号配置，以及手推清扫车状态下的静态/动态 RTK 测试。但室外测试**全程没有固定解**：模块 4G 未拿到 IP，NTRIP 收不到差分，GGA 质量始终为 1。

## 三、工作进展

### 3.1 RTK 差分链路：从单点解到固定解

#### （1）11-09：定位“输入正常但解算不固定”

现场检查结论是“两头都通，中间断了”：

- 串口输入正常：`/dev/ttyACM3`、115200，吞吐约 4.3 KB/s，KSXT/THS 约 10 Hz，582 条报文校验和全部通过；
- CORS 账号正常：两个挂载点均返回 `ICY 200 OK`，服务器在推流；
- 模块内 NTRIP 参数正常：host/port/mount/账号与文档记录一致；
- 但模块 4G 没有 IP，NTRIP 客户端停在 `wait IP_READY`，接收机只能单点解。

进一步定位到 VRS 类 CORS 的握手要求：**必须先上传 GGA，服务器才会下发差分**。原实现“先等应答、再发 GGA”，双方互等，60 秒零字节。

完成 `rtk_driver` 的 NTRIP 客户端落地：

| 文件 | 改动 |
|---|---|
| `rtk_driver/ntrip_client.py` | 新增 NTRIP 客户端：握手、GGA 上行、RTCM 下行 |
| `rtk_driver/run.py` | 新增 9 个 `ntrip_*` 参数、后台线程、GGA 抓取、优雅退出 |
| `rtk_driver/device_interface.py` | 新增 `write_bytes()`，RTCM 二进制直写，不追加 `\r\n` |
| `rtk_driver/node.yaml`、图配置 | 参数声明与配置接入；密码文件不入仓库 |
| `tests/unit/test_ntrip_client.py` | 新增 4 个用例，使用假服务器，不碰外网 |

关键细节：**GGA 抓取放在质量门限之前**。否则单点解阶段会被 `_validate_data` 拦下，永远上传不了位置，服务器也永远不下发差分。

真机验证：KSXT 稳定 10.00 Hz，92 条 GGA 中 89 条为质量 4（固定解），卫星 31，差分龄期 1.0 s。旧账号 11-10 13:20 到期，11-12 已更换新账号（有效期至 11-18）。

#### （2）11-10：SIM 卡与 USB 枚举问题

- 模块日志反复输出 `iccid nil`，说明没有读到卡；同时 USB 出现 `error -71`、`-110` 反复重枚举；
- 更换 USB 口后 ICCID 变为 `89860124801558688985`（联通），确认卡本身可读；
- 该卡当时欠费，缴费复机后仍停在 `wait IP_READY`；后续定位到两个问题：SIM 卡 PIN 未关、以及联通卡最终未能稳定驻网（后续确认**必须使用移动卡**）；
- 为不阻塞实车测试，先用主机 WiFi 连 CORS，写 `ntrip_inject.py` 把 RTCM 注入 UM982 串口，并补上 GGA 保活（否则挂载点约 60 秒踢连接）。注入后 GGA 在 2 秒内从 1 跳到 4。

同一天还发现**双天线整体反装 180°**：手动行驶时 KSXT 航向与实际航迹相差约 180°。在 `rtk_driver` 配置 `heading_offset_deg: 180` 后，自动模式才真正起步。

#### （3）11-12：模块自身 4G/NTRIP 修通

更换新 CORS 账号后，把参数直接写入 Air700E 模块：

```
$snp,120.253.239.161,8002,RTCM33_GRCEJ,<user>,<password>,1,*XX
$snp,ok,*69
$gnp 回读：host/port/mount/user/password 全部为新值
$sne,1,*49  打开 NTRIP 开关
```

- 模块断电重启后 `$gnp` 仍为新值，确认**已固化到 NVM**，无需 `SAVECONFIG`；
- 换上**移动卡**并给模块断电重启后，30 秒采样 22 条 GGA **全部为质量 4**，31 星，HDOP 0.5，`$GNTHS` 航向有效；
- 主机侧 `ntrip_enable` 改为 `false`，避免主机注入和模块 NTRIP 两路差分同时灌入接收机。

至此，RTK 差分不再依赖手机热点，模块可独立完成 4G + NTRIP。

### 3.2 底盘与遥控链路

#### （1）PWM 与运行图

- 40Pin 的 27、28 脚分别对应 `pwmchip0/pwm0`、`pwmchip1/pwm0`，50 Hz、周期 20 ms、中位 1.5 ms；示波器实测两路输出正常；
- 运行图缺少 `path_progress` 节点及连线，导致 `track_controller` 启动即崩溃；补齐节点和 4 条边后 9 个节点全部启动；
- 接入 `web_teleop`，形成 `track_controller → web_teleop.auto_velocity → pwm_driver` 的自动/手动切换链路；
- 清理过一次因节点崩溃触发的 `drive_pwm` 安全锁存（`Drive latch asserted`），否则所有非零指令都会被拒绝。

#### （2）双重混控与方向标定

现象是“前进只动左履带、转向只动右履带”。根因不是混控算法写错，而是**混了两次**：

- 底盘驱动器原本接普通 RC 遥控器，内部已经做坦克混控；
- `pwm_driver` 又按 `differential` 做了一次软件差速。

改为 `drive_mode: direct`：**CH1 = 线速度（油门），CH2 = 角速度（转向）**，混控交给驱动器。随后现场实测前进/后退、左/右转均与摇杆相反，在配置中加 `invert_linear: true`、`invert_angular: true` 修正。

#### （3）遥控延时与“松手不停车”

11-12 出现“轻触 0.5 秒、电机转约 2 秒”的严重延时。定位过程：

- 指令一旦到达节点，PWM 回中位只需 **8–32 ms**，软件执行链路没问题；
- 日志出现 10 次 `Command timeout, stopping`，说明**松手的那条零指令根本没送达**；
- 超时兜底为 `web_teleop` 1.0 s + `pwm_driver` 0.5 s ≈ 1.5–2 s，与现象吻合；
- 指令流实测有 400–900 ms 空档：一个卡死的 `fetch` 会让 `controlInFlight` 永久为真，200 ms 心跳停发。

修复（前端 `static/index.html` + 服务端 `run.py`）：

| 改动 | 作用 |
|---|---|
| `fetch` 加 400 ms `AbortController` 超时 | 单个请求卡死不再堵死通道 |
| 同一时刻只允许一个请求在途，结束补发最新值 | 防止请求堆积 |
| 心跳 200 ms → **50 ms 固定重发**（非零时） | 按住不动时指令不再停在旧值 |
| 松手/急停/重置 → **连发 3 次零指令** + `sendBeacon` | 单次丢失不再导致继续跑 |
| 服务端 HTTP/1.1 keep-alive + `Content-Length` + `no-store` | 手机端不必每请求重建 TCP |
| `command_timeout` 1.0 s → **0.3 s**，输出 10 Hz → 20 Hz | 万一丢包，最多多走 0.3 s |

修复后现场反馈“问题基本缓解”，停车指令到 PWM 中位的实测延迟为 8–32 ms。

#### （4）运行图热加载

新增 `runtime start-dataflow --preset NAME` / `restart-dataflow --preset NAME`，把 `preset_yaml` 透传给 runtime，白名单从 `examples/` 扩到 `configs/graphs/` + `examples/`。实测切换预置图时 **runtime PID 全程不变**，不再需要为了改一张 YAML 重启整个框架。

### 3.3 实车自主行驶与“走走停停”排查

11-11 在室外平整场地完成实车测试。测试前先解决三件事：RTK 固定解（主机热点注入）、两点直线路径生成、自动/手动切换与急停确认。

#### 测试结果

| 测试 | 内容 | 结果 |
|---|---|---|
| A 控制链路 | 手动/自动切换、左右 PWM 通道响应 | 通过 |
| B 短距离直线 | 23.3 m 两点直线，自动起步到终点停车 | 通过 |
| C 重复直线 | 同一条 23.3 m 直线重复一次 | 通过 |
| D 路径转弯 | 右转约 45°，随后直行 6 m | 到点，但实际为弧线，非干净原地 pivot |
| D 转弯后直线 | 转弯后 10 m 直线 | 通过 |

关键指标：

- **直线第一次**：用时 123.8 s，轨迹 24.01 m，均速 0.194 m/s，最大横向偏差 0.26 m，终点误差 0.33 m；
- **直线第二次**：用时 126.9 s，轨迹 24.19 m，均速 0.191 m/s，最大横向偏差 0.28 m，终点误差 0.40 m；
- **45° 转弯**：总用时 148.9 s，其中约 76 s 在等待航向质量恢复；终点误差 0.35 m，实际轨迹 13.12 m（规划 9.0 m），走成大弧线；
- **转弯后 10 m 直线**：用时 52.7 s，轨迹 9.93 m，均速 0.188 m/s，最大横向偏差 0.15 m，终点误差 0.35 m。

两次直线的用时差约 2.5%，横向偏差差 0.02 m，**重复性良好**；四段测试均正常 `arrived` 并回中位，没有出现无法解释的中途停车。

#### “走走停停”的三个原因

1. **35° 航向保护**：作业模式下航向误差 ≥35° 且 `allow_work_pivot=false` 时，`track_controller` 返回 `needs_reposition`，速度归零。11-10 两次分别为 41.1°、37.16°。
2. **pose 超时误判**：`coord_transform.pose_enu` 实际约 3.6 Hz 更新，age 峰值 0.61–0.74 s，原 `pose_timeout=0.5 s` 会把正常抖动判成 `stale_pose`。
3. **USB 掉线**：11-11 15:14:35 模块 USB 重新枚举，造成 0.9 s KSXT 断点，控制器 `stale_pose` 停车。

对应处理：转弯测试启用 `allow_work_pivot=true`；三个超时统一改为 1.0 s；更换 USB 口后继续观察。11-11 后续直线与 10 m 测试未再出现掉线。

#### 转弯为什么是弧线

45° 转弯启动瞬间，双天线 `heading_quality` 掉到 2，`heading_valid=false`，pose 中断约 76 s；控制器进入 `pivot_timeout`，没有完成原地 45°。航向恢复后控制器“边走边转”，最终形成大弧线。**到点不等于动作合格**，这一点在实验报告中已如实标注。

### 3.4 执行机构标定

11-12 用“指令侧 + PWM 输出侧 + RTK 实际侧”三路同步采集，完成油门和转向标定。

#### 油门（CH1）

| 脉宽 | 偏移 | 实测速度 |
|---|---|---|
| 1.500 ms | 0 | 0 |
| 1.369 ms | 0.131 ms | 0.43 m/s |
| 1.297 ms | 0.203 ms | 0.67 m/s |
| 1.166 ms | 0.334 ms | 0.99 m/s |
| 1.036 ms | 0.464 ms | 1.52 m/s |
| **1.000 ms** | **0.500 ms** | **1.61 m/s** |

拟合：`v ≈ 2.94 × 偏移(ms) + 0.09`。指令 1.0 m/s 实际约 **1.56–1.61 m/s，增益约 1.56×**；死区几乎为 0。

#### 转向（CH2）

| 指令 rad/s | 实测 | 折合 |
|---|---|---|
| 0.5 | 4–5 °/s | 0.07–0.09 |
| 1.0 | 27.6 °/s | 0.48 |
| 1.5 | 49 °/s | 0.86 |
| 2.0 | 66–68 °/s | 1.15–1.19 |
| 3.0 | 96–98 °/s | 1.67–1.71 |
| **4.0** | **124–126 °/s** | **2.16–2.20** |

拟合（|cmd| ≥ 1）：`ω ≈ 0.561 × cmd`。满杆 4.0 rad/s 实际约 **2.2 rad/s，增益 0.56×**；0.5 rad/s 以下明显偏离直线，近零有死区。

#### 左右履带天然差异

纯直线段（角速度指令 = 0）的航向漂移：

| 指令 | 速度 | 漂移 |
|---|---|---|
| +1.0 | 1.60 m/s | **+1.1 °/s** |
| −1.0 | 1.59 m/s | **−1.1 °/s** |
| +0.5 | 0.94 m/s | +0.67 °/s |

漂移符号随行驶方向翻转，说明是**两侧履带速度差**（约 `Δv ≈ 0.01 m/s`，0.6%），不是地面起伏；天线安装偏角只会造成恒定航向误差，不会造成漂移。后果是跑 10 m 航向偏约 7°、横向偏约 0.6 m，后续应由在线 trim 吸收，而不是写死在配置里。

> 标定条件：磷酸铁锂电池 79.3 V（满电 87.6 V 的 90.5%）。直流电机转速大致正比电压，表中速度约比满电低 10%，换电池或充电后需复检。

#### 数据质量问题

标定过程中出现两次 `$KSXT` 冻结：run3 中段冻结 **129 秒**；run4 在高速转向（指令 3.0–4.0 rad/s）时冻结。判断为 **USB ACM 在电机大电流/EMI 下卡死**，不是 WiFi 问题。采集脚本已加自愈（超过 1.5 s 没收到 KSXT 就重开端口），但 **`rtk_driver` 节点本身还没有自愈**，这是产品级隐患。
