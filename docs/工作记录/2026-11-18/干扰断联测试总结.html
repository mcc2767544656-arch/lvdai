2三次“假异常”，根因在测量工具

这三次都一度看起来像故障，查下来都是监测脚本自身的问题，已全部修复。

时间现象根因处理
15:40:47 1.04 s 断流 脚本在串口读取循环里同步执行 ping，一次超时把循环阻塞了 1 秒，时间戳被拉长。 ping / WiFi 探测移到独立线程，复测后消失。
16:16–16:22 298 条坏帧 串口里的 #HEADINGA 是 NovAtel 格式日志，被当成 NMEA 语句做校验。 只校验 $ 开头的语句，坏帧归零。
16:12–16:15 约 3 分钟无数据 反复开关 /dev/ttyACM3，且有多个进程同时抢读同一个串口。 静置 5 分钟无自发断流，判定为操作所致，非模块故障。
为什么要写下来：这三条都不是设备问题，但形态和真故障几乎一样。以后再看到“断流 / 坏帧”，先确认是不是测量方式造成的，再下结论。

4这次没覆盖到的

以下四点决定了今天不能下“问题已解决”的结论，只能下“本次未复现”。

  • 工况不同：原地打滑的电流、振动、履带负载都小于实际行驶与高速转向（11-12 的冻结发生在指令 3.0–4.0 的高速转向）。
  • 耦合路径不同：测试时 Pi 未参与驱动、PWM 线不接驱动器，线束布局与实车不一致。
  • 无卫星：地下车库 0 星，解算层（定位质量、差分龄期、SNR）本次没有观测到。
  • 未直接测供电：没有测量 5V 轨的电压跌落；USB 无事件只能排除“被拉挂”，排不掉“缓慢掉压”。
下一步：室外有固定解后，用合并版监测跑真实工况（直线 + 转向 + 负载），把“基线 / 转动”区间分开对比；测试时记录开始/停止时间点，便于对齐。
